# 经验教训库 (AI参考)

## v5.4.6 事故复盘：v3.9.0 的实现被重构删掉，静默降级让它伪装成"设计"

### 问题现象

YouTube 视频的 D2(时效) 与 D3(互动) **全部为 0**（近 35 天 208/208 条），
评分长期退化成 `(D1+D4)/2`。而飞书里 `Views` 数据齐全（206/208 条 > 0）。

### 踩坑记录

- ❌ **"文档写着有"≠"代码里有"；"代码里没有"≠"设计上不该有"（本次核心教训）**：
  我第一轮只读了 README（写着"YouTube 也计算 D2/D3，数据从飞书回填"）就下结论"实现落空"，
  用户当即纠正：**"不要只依赖 README，很多更改没有写入 README"**。
  - ✅ 正确姿势：判断"某功能该不该存在"，要查**四类考古现场** ——
    ① `CHANGELOG`（历史决策）② `scoring.py` 等核心文件的头部版本注释
    ③ `_deprecated_*.py` / `*_vX_backup*.py`（旧实现可能还躺在那）
    ④ `tools/` 下的独立脚本（常常是为补某个洞写的一次性工具）
  - ✅ 本次正是靠第 ③ 类找到决定性证据：`_deprecated_video_subtitle_censor7.py:1095`
    明写着 `# v3.9.0: YouTube视频从飞书回填统计数据（抓取阶段已写入飞书但字幕阶段丢失）` + 完整实现；
    第 ④ 类找到 `tools/yt_enrich.py`（专门的补偿工具）。四重证据一致才敢定性。

- ❌ **静默降级会把"坏掉的实现"伪装成"有意的设计"**（这是最危险的地方）：
  旧回填代码的 `except` 只打一句 `WARN ...将使用默认值，D2/D3可能为0`，
  于是 **D2/D3 恒为 0 这个明显的异常，被日志的"友好提示"合理化了** ——
  后续任何人看到"可能为0"都以为是已知的、可接受的降级，没人去查。
  - ✅ 铁律：**降级日志必须写清"后果 + 是否需要人工介入"**，
    而不是写成"可能为0"这种既像正常又像异常的中性措辞。
  - ✅ 更根本的：**关键维度长期恒为 0 应该触发断言/校验**，而不是安静地算出一个偏低的分数。

- ❌ **`FeishuSync()` 必须紧跟 `set_bitable_token()` —— 本项目反复踩的同一个坑**：
  旧回填代码只写了 `_sync = FeishuSync()`，没设 token → `get_record_by_field` 必然报
  "bitable_token 未设置" → 被 except 吞掉。**功能从来就没真正生效过**。
  - ✅ 这个坑在 `core/CHANGELOG.md` 里已有记录（"URL 中 `apps//tables` 有两个斜杠"），
    说明**同一个坑踩过多次**。写飞书代码前先确认 token 已设置。
  - ✅ 写验证脚本时也踩了同一个坑（`diag_bili_date_tmp.py` 首次运行报 "bitable_token 未设置"）。

- ⚠️ **"补数据"和"改口径"必须一起考虑，否则修一个 bug 引入另一个**：
  只回填 `Views/Likes/Comments` 而不给 D3 加样本门槛，`views=5` + 1 个赞
  就会算出 >10% 互动率 → **D3 满分 10** → 总分被推到 19.5。
  - ✅ 加门槛后：`views=5/14/99` → D3=0；`views=100` 起才计分。
  - ✅ 经验：**引入"比率类指标"时必须同时设分母门槛**，这与本项目在报表场景
    （"视频级比率门槛=观看≥100"）的既有约定是同一个道理 —— 那条约定当时只落在了报表上，
    评分里的 D3 一直裸奔。

- ⚠️ **补全的值要写回原对象，否则"补全"只在一处生效**：
  `calculate_video_score` 在同一流程内被调用 3 次（fetch 阶段 / `submit_ai_tasks` / `process_ai_results`），
  若不把补全结果写回 `video_info`，每次都要重查（虽然缓存挡了 API 请求，但日志会重复、且其他地方读 `video_info['views']` 仍是 0）。
  - ✅ 修法：补全成功即写回 `video_info`，后续调用自然短路。

## v5.4.5 补充复盘：YouTube 侧同类检查（数据源不同 → 风险不同）

### 结论先行

用户问"B站 的发布日期问题在 YouTube 侧是否也存在"。实测近 35 天 252 条正向标记：
**`Published Date` / `Published At` / `Duration` 全部 0 不一致**。

原因：**两者数据来源根本不同** ——
- B站：`parseDate()` 解析**搜索页的文本**（`3天前` / `9月16日`）→ 页面改版就崩
- YouTube：直接取官方 API 的 `publishedAt`（UTC ISO）+ 固定时区换算 → 不存在文本解析

### 踩坑记录

- ❌ **不要假设"同类问题会到处都有"，先看数据来源**：
  「发布日期错误」在 B站 是"文本解析失败 + 兜底伪造"，在 YouTube 是"官方结构化字段"，
  两者的失效模式完全不同。**同一个业务概念（发布日期）在不同平台的可靠性取决于其数据来源**，
  排查时要先画出"这个字段从哪来"，再判断风险。

- ❌ **"字段值与 API 不一致" ≠ "写错了"，必须先区分"快照时效"与"错误"**：
  `Views`/`Likes`/`Comments` 有 206/138/61 条与 API 不等，看方向就能定性：
  199 条是"飞书 < 真实"（快照后视频继续涨）→ 正常；
  7 条"飞书 > 真实"（YouTube 会周期性清理无效播放量，`viewCount` 确实会回落）→ 也正常。
  - ✅ 判据：**单调方向差异 = 快照时效；双向乱跳 = 写入错误。**
  - ✅ 飞书存的是"抓取那一刻"，不是"实时"，**不要拿实时 API 去断言它错**。

- ⚠️ **对比脚本自身的归一化不一致，会造出"假差异"**（浪费了一轮排查）：
  第一版脚本里 `fb_ch = str(...).strip()` 但 API 值没 strip，于是 6 条"频道名不一致"
  打印出来两边长得一模一样 —— 实际是 YouTube 官方 `channelTitle` 自带尾随空格。
  - ✅ 铁律：**对比两个来源的字符串前，先明确"是否对两边做了同样的归一化"**；
    不一致时打印 `repr()` 与字符码点，别只看肉眼看不出差别的字符串。

- ⚠️ **类型判断会静默漏判（`isinstance` 陷阱）**：
  飞书的 `Views` 字段实际是 **text(1)** 而非 number，值形如 `"4530"`（字符串）。
  用 `isinstance(v, (int, float))` 分类"增长/下降"时会**全部落空**，
  统计结果显示 `正常增长 0 / 异常 0` 却又"总不一致 206" —— 自相矛盾的数字就是线索。
  - ✅ 结论：**统计口径里出现"分项之和 ≠ 总数"时，优先怀疑类型判断而不是数据。**

- ❌ **"中间态标记"缺少终态收敛 —— 这是本项目第二类系统性问题**：
  `Human Prescreen = Selected/High Priority` 是 **ScriptDedup 阶段**的产物（表示"被选中送审"），
  但 AI 环节若失败（无字幕），**没有任何代码把标记回滚** → 标记停在"入选"，
  数据却是空的（`Subtitle Status` 空 / `Total Score = 0`）。
  实测近 35 天 44 条（17.5%）如此，横跨 08/17 ~ 09/14 各批次。
  - ✅ 通用规则：**任何"先标记、后处理"的流程，都必须有"处理失败时如何收敛标记"的终态定义**；
    否则标记会漂移成谎言。本项目里 B站 侧靠 `_sync_youtube_failed_status` 之类补写，
    YouTube 侧之前因缺 `video_id` 而静默跳过（v5.4.3 才修）。
  - ✅ 排查手段：用**跨字段一致性断言**找它 ——
    "标记 ∈ 正向集合 但 `AI Review Report` 为空"这种组合本身就是异常，
    比看单个字段更容易发现（本次就是靠这个筛出 44 条）。

- ⚠️ **别把"流程未完成"和"评分不达标"混为一谈**：
  筛出来的 44 条里，42 条视频**真的没有字幕**（终态，无法审核）；
  另外 1 条（`视频E`）是"AI 已完成但 54 分钟超长 → D1=0 → 总分 0"，
  属**正常的不达标**，不该被当作异常处理。
  - ✅ 处理前先按"能否补救"分类：**可补救的补跑、真终态的补状态、正常不达标的别动**。
    本次先逐条实取字幕（`youtube-transcript-api`）才敢下结论，避免误伤。

- ⚠️ **补跑路径缺统计数据回填，会系统性低估分数**：
  `fetch_and_process_single` 单条路径未回填 `views` / `publish_time`，
  导致 D2（时效）与 D3（互动）恒为 0，总分被算低（本次两条分别 0.0 / 5.95）。
  本次结论不受影响（D1 已决定结果），但**若用它去"抢救"本应入选的视频，会误判为不达标**。

## v5.4.5 事故复盘：解析失败"兜底返回当天"污染整批发布日期

### 问题现象

用户反馈 B站「发布日期」不对。实测 2026-09-20 批次 **23/23 全部**写成抓取当天，
而真实发布时间从 2024-09-27 到 2026-09-17 不等；对照官方 API 抽样 20/20 全不一致。

### 踩坑记录

- ❌ **解析函数的"兜底分支"绝不能返回一个"看起来正常"的假值**（本次事故主因）：
  `parseDate()` 用 `if/else if` 逐条匹配格式，最后无条件 `return` 当天日期。
  当 B站把日期文本从 `09-14` 改成 `9月14日`、新增 `3天前` 时，28/42 张卡片全部命中兜底，
  **静默产出"抓取当天"**——不报错、不告警、数据看起来完全正常。
  - ✅ 铁律：解析失败必须**显式失败**（返回空/抛异常/记 WARN），**永远不要用"当前时间"当兜底值**。
  - ✅ 通用规则：`parse*()` 的 else 分支返回"合理但不正确"的值（当天/0/空对象）是最危险的失败模式，
    因为它不会被任何断言发现。
  - ✅ 发现手段：**按维度做"分布异常检测"**。本次是"按创建时间分组 → 看发布日期唯一值数量"，
    09/20 批只有 1 个唯一值 → 一眼看出异常。比分批抽样比对更快更准。

- ❌ **依赖第三方页面文本格式的解析，必须定期实测原始文本**：
  旧代码写了 `前天` 却漏了 `2天前`；写了 `MM-DD` 却漏了 `M月D日` ——
  说明当初是"照着想象写格式"，没有 dump 真实文本。
  - ✅ 正确姿势：先 Playwright 打开页面 **dump 全部卡片的原始日期文本 + 取值分布**，
    再按真实分布写分支（本次实测 42 张卡片共 9 种文本，其中 4 种旧代码不认识）。
  - ✅ 同时把"兜底正则"一起补齐 —— 否则主选择器失效时会静默退化。

- ⚠️ **网页只给相对时间时，"日"粒度天然有 ±1 天歧义**：
  `X小时前` 是**向下取整**的，真实偏移 ∈ [X, X+1) 小时。当 `now - Xh` 与 `now - (X+1)h`
  跨越午夜时，无法唯一确定日期（本次 5 条 `18小时前` 因此差 1 天）。
  - ✅ 取**区间中点**（`now - (X+0.5)h`）可最小化跨日误差，实测把 5 条偏差降到 0。
  - ✅ 要彻底消除，只能用权威源（官方 API `pubdate`）校准。若业务只要求"日"精度，
    中点估计是成本最低的折中；但**必须知道这个歧义存在**，不要以为解析对了。

- ⚠️ **同一个"日期"在系统里有两个来源时，要确认它们各自喂给了谁**：
  B站发布日期有两条链路 —— ① 抓取端（Excel→飞书 `发布日期`，来自网页文本）；
  ② 评分端（`bilibili_client` 官方 API `pubdate`）。本次 ①错了而 ②是对的，
  所以 **D2/总分没有被污染**，但 **机器初筛的 ">21 天" 过滤被绕过**（它读的是 ①）。
  - ✅ 排查影响面时，先画清"这个字段被谁读"，再逐条判断后果，不要笼统说"数据全错了"。

- ⚠️ **写 DATETIME 字段时，值为空要"跳过字段"而不是写空串**：
  `push_to_bitable` 原先在类型判断之前就把 NaN 转成 `""`，会把空串写进 datetime 列。
  本次顺手修正为 `ft == 5` 时直接 `continue`（不发送该字段）。

## v5.4.4 事故复盘：同一频道在同语言下多次入选（分组键 / 覆盖写 / 统计范围）

### 问题现象

用户反馈"某语言明显 >8，同一频道仍入选多次"。实测本批：英文 18 条里 频道A 占 3 条、
频道B 占 2 条；B站中文 10 条里 频道C 占 2 条。

### 踩坑记录

- ❌ **"未知值"绝不能自成一组并享受独立配额**（本事故主因）：
  ScriptDedup 用**视频声明语言**（`Language`：en/de/ru/zh/**N/A**）分组，每组各有一份
  「每频道 1 条」+「<8 就补足到 8」的配额。于是同一频道的视频只要有一部分是 `N/A`，
  就能在 `N/A` 组**再拿一份配额** —— 频道A 的 3 条同属一个 Channel ID，却分属 `en`(1)/`N/A`(2)。
  - ✅ 正确做法：**未知值不创建新配额**。先尝试归入"该实体已知的归属"（这里是：该频道在本批出现过的已知语言）；
    实在无法归属才进"补充位"，且**只允许尚无代表的作者补 1 条**。
  - ✅ 通用规则：`groupby(key)` 时，若 `key` 为空/未知，**不要**把它当作一个正常分组值参与配额分配。

- ❌ **同一概念在不同阶段取值口径不同，是结构性错配的温床**：
  ScriptDedup 跑在 AI 之前，读不到 AI 判定的「语言_Language」，只能读声明语言 ——
  所以"按语言去重"这件事**不可能只靠 ScriptDedup 做对**。
  - ✅ 结论：这类"判定依赖后置信息"的约束，必须在信息可得之后再补一次**事后收敛**（本次的兜底校验）。

- ❌ **"事后覆盖写"必须检查当前状态**：
  来源视频翻转 `_flip_source_priority` 只判断「AI 已完成 + 在注册表」，无视当前 `Human Prescreen`，
  把一条已被去重判为 `Rejected` 的视频又翻成「高优先级」→ 绕过全部去重。
  - ✅ 铁律：任何"翻转/复活/覆盖"动作前，先读当前值并按状态短路（本次加 `[FLIP-SKIP]`）。

- ❌ **带"总数超过 N"条件的规则，必须先定义统计范围**（差点造成大面积误伤）：
  兜底校验首版没限定窗口，dry-run 一扫全表 → 显示要收敛 **194 条**（B站）/ **51 条**（YT 英文）历史记录；
  而规则本意只是"**每周批内** >8 才限 1 条/频道"。
  - ✅ 加"本批窗口"（优先运行锚点=上次运行结束，无锚点回退天数）后，收敛数正确降到 **4 条**。
  - ✅ **教训：批量改数据前先 dry-run 看规模，规模与预期不符就是设计错了，不要硬跑。**

- ⚠️ **"补足到阈值"的逻辑会让结果精确贴住阈值**：
  `有效入选 < 8 → 补到 8`，于是每个语言组的最终数**恰好 = 8**，永远贴着规则边界
  （俄文 8 条里 Average 占 4 条；zh 组 4 条全是频道D）。
  阈值两侧语义相反（`≤8` 允许重复 / `>8` 禁止重复）时，这种"贴线"设计极其脆弱 ——
  一旦后续 AI 通过数增加 1 条，就从"合规"翻成"违规"。**边界附近不要做等号设计。**

- ✅ **Notes 字段就是"决策日志"，是排查这类问题的第一现场**：
  每条记录的 Notes 累积着历次运行的 `Kept/Dropped` 结论（`Kept: latest of 3 from UC…`、
  `Kept: fill to 8 (from Dropped: …)`）。仅凭它就能还原"分组 → 决策 → 补足"全过程，
  无需重跑流程即可定位机制。**排查前先读 Notes。**

- ✅ **桩测试是验证分组/去重逻辑的高性价比手段**：
  覆写数据源（候选池）后用**真实代码**跑分组、去重、补足、写回，只把飞书写入换成桩。
  本次据此复刻 频道A 场景，断言"同频道只留 1 条"，一次跑通即定论 ——
  比"等下周真实数据"快得多，也能覆盖边界（纯未知语言频道）。

### 复盘结论

- 分组键为空/未知时，**不得**作为一个正常分组参与配额分配。
- 依赖后置信息的规则（语言判定、AI 结果），必须在信息可得后**补一次事后收敛**。
- 任何覆盖写之前，先读当前状态并按状态短路。
- 带"总数阈值"的规则必须显式声明**统计范围（本批 / 全史）**，且改数据前先 dry-run。
- Notes 是决策日志：先读它，再动手。

## v5.4.3 事故复盘：失败结果缺 video_id，飞书失败标记全被静默跳过

### 问题现象

本轮 8 条 `no_subtitle` 视频在飞书里 `Subtitle Status` 一直是**空**；同期 `rahhdTkIkwg`
（AI 阶段失败）却被正确标为 `failed` —— 同一套标记逻辑，一半生效一半不生效。

### 踩坑记录

- ❌ **"字段缺失 + 静默跳过 + except pass" 是最难查的沉默失败组合**：
  `_sync_youtube_failed_status` 内部是
  `if not video_id: continue` → 空跳过；外面又包了 `except Exception: pass`。
  结果：v5.3.4 引入的"失败视频回写飞书"功能，对**整条 no_subtitle 失败路径从未生效过**，
  日志里连一行 WARN 都没有。**"看起来什么都没发生"往往就是代码走了静默分支**。

- ✅ **根因是一处字段缺失，不是逻辑错**：`fetch_and_process_single` 的失败分支返回
  `{input, success, error, platform, has_subtitle}` —— **没有 `video_id`**；
  `_youtube_base_result()` 同样不含 `video_id`。上游取不到 ID，下游只能跳过。

- ✅ **同一份数据在不同分支口径不一致 = BUG 温床**：成功分支带 `video_id`（第 415 行 `video_info['video_id']`），
  失败分支不带。**排查时不能只看"正常路径"。**

- ✅ **改动要挑"非破坏性"的接口**：`fetch_youtube_subtitle` 有 4 处调用方按 2 元组解包，
  直接加第 3 个返回值会连带炸掉 4 个文件。改为**把 `error_category` 写回结果字典**
  （`_stamp_error_category`），签名不变、调用方无感 → 最小改动面。

- ✅ **修完必须用真实请求验证，不能只看编译过**：`py_compile` 通过、静态检查 0 处，
  都只能证明"不报错"。真正验证是跑一条已知失败视频，断言
  `video_id == 'TEBThZNTstI' 且 error_category == 'no_subtitle'`。

- ✅ **写飞书前先看"同类历史记录长什么样"**：本轮要标 8 条无字幕终态，先查现存 21 条同类记录，
  发现它们**只写 `Subtitle Status`，其余字段全空** → 照抄，而不是自己发明
  "AI Review Result=unsafe + 报告写 WARN..." 的写法。**先找先例，再动手写。**

- ✅ **手写字面量字段名会伪造出"字段不存在"的假象**：排查脚本里手写中文 `"视频ID"`/`"Human Prescreen"`
  去取值，结果全部打印"(字段不存在)"，差点据此得出"飞书数据缺失"的错误结论。
  YouTube 表实际是英文名（`Video ID` / `Prescreen Status` / `Total Score`…）。
  对照实验才发现：用 `YT_F_VIDEO_ID` 常量建的索引是**命中的**，说明字段存在、只是我名字写错了。
  **一律用 `core/feishu_fields.py` 常量。**

- ✅ **"节点风控"与"视频级终态"必须用对照实验区分**：本轮 8 条 `no_subtitle` 是否真是终态？
  做法：先跑 2 条**本轮已成功审核**的视频作对照（2/2 成功 → 节点正常），
  再跑这 8 条（在节点正常前提下仍稳定失败）→ 排除 IP 因素，判定为视频级终态。
  佐证：抓取阶段写入的 `Has Captions = No` 与失败结论一致。
  **不要用"换个节点试试"的模糊说法下结论，要用对照。**

### 复盘结论

- 任何"回写状态/标记"的功能，必须保证**失败分支也携带必要的定位字段**（如 video_id）。
- 静默 `continue` + `except: pass` 组合必须加日志，否则等于没有这个功能。
- 判定"终态 vs 可重试"必须有对照实验，不能凭单次报错下结论。
- 写飞书前：先读字段类型 → 再找同类历史记录当模板 → 再写 → 再回读校验。

## v5.4.2 事故复盘：滑动窗口与运行节奏错位（本周入选量虚低）

### 问题现象

用户反馈"本周通过流程的视频数量偏少、不正常"。实测：YouTube 新增 145 条 → 最终仅 10 条通过 AI 审核（上周是 34 条）。

### 踩坑记录

- ❌ **"用固定 N 天定义本批"是伪需求陷阱**：ScriptDedup 原本用 `cutoff = today - (days_filter-1)` 同时表达两件事——"哪些是本次要处理的候选"和"哪些算本周期已标记"。但这两件事的时间边界**根本不同**：
  -"候选池"的边界是「上次运行之后写入」
  -"已标记"的边界是「上次运行产出之后被标记」
  用同一个数字硬凑，必然在某个运行节奏下出错。
  - ✅ 实测触发条件：两次运行间隔 ≤6 天时，上次产出日恰好 = `today-6` = 窗口起点 → 上次的 45 条 Selected 被算作"本周已标记 UP" → 其 25 个频道本周的 102/145 条候选被整批排除。
  - ✅ 上周没触发**纯属巧合**（间隔 7 天，上次产出日 09-07 比窗口下界 09-08 早一天）。**依赖巧合的正确 = 潜在 BUG**。

- ✅ **正确的锚点是"上次运行"，不是天数**：用户可能提前或延后启动工作流，任何固定天数都会在某个节奏下失效。改为记录上次运行的 `start`/`end` 时刻（`data/run_anchor.json`）：
  - `pool_cutoff = last_run.start` → 上次中断未处理的记录也能被本次接住（不漏）
  - `marked_cutoff = last_run.end` → 排除上次运行自身的产出（不误杀）
  两个下界**必须分离**，这是修复的核心。

- ✅ **锚点只在完整成功时写入**：若中途失败也写锚点，下次窗口会从"上次结束"开始，而上次未处理的记录（写入时间 < 新锚点）会被永久跳过 → **漏处理**。失败时保持旧锚点，窗口自然覆盖更长时间，只是候选池略大。

- ✅ **诊断要用「交叉验证」而非单点观察**：本次先看到"保留 42→11"（可疑），再验证"已标记 45 条全是 09-14 写入"（确证），再交叉"本周新增频道 ∩ 上周入选频道 = 25 个 / 102 条"（量化影响）。三步下来根因无法辩驳。**单看任一数字都可能被误判为"数据波动"**。

- ✅ **飞书 search 接口的坑（诊断时踩到）**：
  - `page_size` / `page_token` 必须走 **query 参数**；放 body 里会被忽略 → 每页返回同一批数据且 `has_more=true` → **死循环累积**（曾累积到 15 万条假记录）。
  - `automatic_fields` 必须显式为 `true`，否则 auto_number（序号）等自动字段**不返回**。
  - 无过滤的全表分页在表变大后耗时明显；诊断"最近 N 天"应用 search + 日期 filter（`{"operator":"isGreater","value":["ExactDate", ts]}`）。
  - ⚠️ 日期字段**不支持 `isLess`**（带该条件会返回 0 条），上界需在 Python 侧过滤。

- ✅ **飞书 `Number` 字段（自动编号, type=1005）是可靠的批次判别依据**：
  - API 返回的是**字符串**（如 `'14060'`）→ 必须 `str(...).strip().isdigit()` 再转 int；用 `isinstance(n, int)` 判断会**静默漏掉全部**（这正是最初"序号对不上"的假象来源）。
  - **search 接口不带 filter 时返回的 `Number` 是位置序号（1,2,3…）假值**；带 filter 或走 `GET /records` 才是真实编号。
  - 同一批由 Fetcher 连续写入 → Number 必然是**连续区间**。实测：上周 `13899~14059`（161 条）、本周 `14060~14204`（145 条），**无缝衔接**，与日期分组的批次划分完全一致 → 可用于交叉校验锚点边界是否正确。
  - 相较时间戳，Number 不依赖本地锚点文件、不受时区/时钟影响，是更"硬"的校验依据（但需额外查询，故当前仅作为日志校验而非主锚点）。

- ✅ **重置范围要精确**：只重置"机器初筛通过 + 人工初筛=拒绝"的记录（ScriptDedup 的产物）；机器初筛拒绝的记录人工初筛本就为空，不应纳入。本次 97 条（YouTube 86 + B站 11）与日志计数精确吻合，是判定正确的有力旁证。
- ✅ **只清"人工初筛"，不清 Notes**：Notes 中可能有来源标注行，且 ScriptDedup 重跑时会以 `_merge_notes` 追加更新。

### 复盘结论

- 涉及"本批/本周期"语义的边界，**禁止用固定天数实现**，应锚定到真实事件（上次运行/上次批次）。
- 同一函数里用一个变量表达两种语义边界时，先问"这两件事的时间边界真的一样吗"。

## v5.4.0 来源视频全流程化（后置翻转优先级）经验教训

### 关键设计决策

1. **优先级加权与字段翻转解耦（评分时加权 / AI 后翻转）**: 若等 AI 审核完才把 Human Prescreen 翻转为 High Priority 再评分，则评分时拿不到 +10 加权；若前置写字段，AI 失败的视频会以"高优先级 + AI 空"混入审核池。解法：评分时从 `source_registry.json` 直接读来源给 High 权重（`video_processor.py`），字段翻转推迟到 AI 审核真正完成后（`workflow_orchestrator._flip_source_priority`），两个动作完全解耦。

2. **来源信息存本地注册表而非 Notes 字段**: Notes 会被 ScriptDedup 的去重备注、复活标注等多处写入，任何"整段覆盖式"写 Notes 的代码都会悄悄抹掉来源标注。SSOT 单独落 `data/source_registry.json`（线程锁 + 幂等注册 + 旧格式兼容），Notes 只做人类可读的辅助标注；ScriptDedup 改为 `_merge_notes` 追加合并。

3. **复活候选的过滤口径必须是"机器初筛拒绝 + 当周写入 + 来源注册表命中"**: 机器初筛 Reject 是 ScriptDedup 淘汰的来源视频的正常去向；复活的本质是"豁免一次去重"，不是"豁免全流程"——复活后必须补跑 AI，通过后才翻转优先级。D1+D2 降序取前 (8-ai_done) 条避免复活无限膨胀。

4. **标记阶段前移（Stage 2.1 → 1.5）是补录视频当轮闭环的前提**: 若 Discord 补录发生在 Prescreen 之后，补录的新记录只能等下一轮才被初筛扫到。前移到 Fetcher 之后、Prescreen 之前，补录视频当轮即可走完 初筛 → 去重 → AI 全流程。

5. **删除前置写优先级时必须同步清理所有消费方假设**: `video_processor.py` 优先级映射文件路径错误（`core/core/...` 双层拼接导致永远加载失败）能长期潜伏，正是因为"前置字段已存在时路径分支根本不执行"。删除前置写入后该分支才被真正激活暴露。

### 踩坑记录

- ❌ 验证断言用 `"Stage 2.1" not in src` 会误伤 docstring 里的历史沿革说明 → 措辞改成"标记类阶段前移至 Stage 1.5"避免残留旧编号
- ✅ dry-run 验证只读飞书（get_records/get_fields），`register_source`/`create_record`/历史写入全部被 `if dry_run` 守卫，满足"验证不修改线上表"约束

## v5.3.5 字幕语言AI分类 + 双源自动标记 经验教训

### 关键设计决策

1. **分类时机前置到"处理单视频时"而非"同步时"**: `classify_by_ai` 在 `fetch_and_process_single` 成功后立即执行（每个 YouTube 视频约 1 次 glm-4-flash 调用），结果挂在 `r['lang_class']` 上随结果流动；`sync_results_to_feishu` 只做写入和兜底。若放在同步阶段批量分类，几十个视频会串行积压 AI 请求，且同步线程池 (5 workers) 内再嵌套 AI 重试会放大超时风险。

2. **"AI 结果为准" + 确定性回退**: hint 代码 (transcript.language_code) 只是参考——实测 D9R0tmFX2Ko 的 Language 字段是 `en`、字幕代码是 `de`、AI 判定 `德文`，说明字段值/代码/AI 三者都可能有偏差，AI 读全文最可靠。AI 3 次全失败时回退 `classify_language_code(hint)`，保证函数永不抛异常、永不返回空（分类失败不阻断审核主流程）。

3. **select 字段全链路传 NAME**: `语言_Language` 从 create_field 的 options 预置、到 update_record 写入值，全部用中文名（"英文"/"德文"…），绝不传 option ID——这是 feishu-write-safety 的铁律（v4.5.1 曾因传 ID 产生 972 条乱码）。写入前 `get_fields` 重新拉表结构确认字段存在才写。

4. **字段存在性双保险**: `init_fields`（stage feishu 入口）+ `main.py _ensure_language_fields()`（sync 入口）两层保障。原因：human-prescreen 主流程（最常用入口）根本不经过 stage feishu，只靠 init_fields 会在首次运行时报"字段不存在"写入失败。

5. **标记类脚本的"命中才记历史"原则**: Discord 自荐消息只有在链接命中 YT 表后才写入 `data/discord_history.json`；未命中的不记——视频往往晚几天才被抓取入库，下次运行可以重新匹配到。代价是 7 天窗口内未命中消息会被重复扫描（无害，纯读操作），换来"延迟入库也能被标记"的正确性。

6. **b23.tv 短链解析必须显式绕过环境代理**: `proxies={"http": None, "https": None}` 强制 bilibili 直连。requests 默认信任 HTTP_PROXY/HTTPS_PROXY 环境变量，而同机代理是给 YouTube/Discord 用的，走代理访问 b23.tv 反而可能失败或变慢。

7. **普通文字频道 vs 论坛频道的接口差异**: videos-n-streams (<DISCORD_VIDEO_CHANNEL_ID>) 是 type=0 文字频道，用 `GET /channels/{id}/messages`（spider_discord.py 处理的 5 个频道是论坛，用 `/threads/search`）。拉回的消息按时间倒序，"触碰历史边界/时间边界即 break" 的剪枝依赖这个顺序。

- ✅ 验证脚本按 Video ID 反查 record_id 写入，逐条打印 AI 判定 vs Language 原值对照，即使重复行也不影响"仅写 3 条"的约束

- ✅ 符合任务规格（只提取两种格式）；如需覆盖 shorts，在 `extract_video_ids` 增加一条 pattern 即可

## v5.3.4 YouTube 智能重试 6 项优化经验教训

### 核心改造: 消除双重请求 + 状态跨轮累积

**改造动机**: 重试流程中同一视频先"探测字幕"又 `fetch_and_process_single` 再取一次（双重请求），且 SmartRetryEngine 在 while 循环内每轮重建，IP 健康度窗口永远基于空窗口，`should_pause_batch` 形同虚设。

**改造结果**:
- ✅ 探测拿到字幕 → `fetch_and_process_single(probe_data=...)` 复用结果，不再二次请求
- ✅ 引擎提升到循环外创建，`record_result` 逐请求记录，IP 健康度滑动窗口跨轮真实累积
- ✅ `attempt_count` 从"轮次号"改为"单视频已尝试次数"（跨轮累计）
- ✅ 两个重试循环统一终止条件 `retry_round > MAX_RETRY_ROUNDS`
- ✅ 失败状态区分：视频级问题 → failed（永久）；ip_blocked 等可重试 → pending
- ✅ IP_BLOCKED 首次重试等待 60s → 0s

**关键设计决策**:

1. **探测结果就是最好的复用数据**: `_fetch_youtube_subtitle_via_transcript_api` 内部自带 3 次 list() 重试 + fetch fallback，探测失败分类已经足够可靠；探测成功则其返回的 `data`（含 subtitle_text/duration）与 `fetch_youtube_subtitle` 返回值结构完全一致，可直接传入 `fetch_and_process_single(probe_data=...)` 跳过二次请求，且不影响评分/AI 流程。
   - ⚠️ 注意：直接调用探测函数绕过了 `fetch_youtube_subtitle` 里的 `_on_youtube_success()` 回调，复用路径必须手动调用一次，否则 YouTube 速率限制器状态会失真。

2. **有状态引擎必须提升作用域**: 引擎（IP 健康度滑动窗口、失败计数、时间预算）是跨轮状态，放进 while 循环内创建=每轮归零。凡是"需要跨迭代累积的状态"，必须提升到循环外；循环内只保留无状态调用（decide/should_pause_batch）。

3. **attempt_count 的语义必须是"单实体已尝试次数"**: 用轮次号当 attempt_count 会在批量场景下把所有视频混在一起——第 2 轮时每个视频都被当成"已尝试 2 次"，与策略表 `max_attempts`（按单视频定义）错位。用 `Dict[url, count]` 按实体计数，跨轮累计。

4. **两个循环写同一套终止语义**: 完整流程（round_num 含初始轮）与单独重试（round_num 从 1 开始）轮次变量起点不同，直接抄条件必然不一致。统一引入 `retry_round`（已执行重试轮数）作为唯一判据，条件字面相同，改 MAX_RETRY_ROUNDS 时不再需要两处联动推理。

**踩坑记录**:
- ❌ 原实现探测成功时 `error_category=""`，`decide("")` 落入 UNKNOWN 策略（max_attempts=1），第 2 轮起被误判"已达最大重试次数"而跳过——一个本应成功的视频被判失败
- ✅ 修复：探测成功直接走复用路径，不再进入 decide()
- ❌ IP_BLOCKED 首等 60s 在批量失败时逐视频累计，几十个失败视频 = 几十分钟纯等待，且等待后同一 IP 大概率仍被封
- ✅ 修复：等待序列 [60.0] → [0.0]，配合"重试一次即失败则标记 pending 待换代理"的流程
- ❌ **报告方法持锁死锁（自检发现）**：`generate_combined_report()`/`generate_phase_report(phase=2)` 在 `with self._lock` 内调用同样加锁的 getter（`get_success_after_retry`/`get_still_failed`），`threading.Lock` 非可重入 → 自检跑到"模拟重试"处永久挂死（表面像"管道没输出"，实际是死锁）
- ✅ 修复：持锁期间内联列表推导统计。**教训：非可重入锁内禁止调用任何会再获取同一把锁的方法（哪怕只读）；重构时把"加锁方法"拆成"加锁包装 + 无锁实现"两层**

**经验总结**:
> 📝 **重试系统的四个检查点**：① 每次请求是否都是必要的（探测≠重复请求）；② 健康度等统计状态是否跨轮累积（别在循环里 new 引擎）；③ attempt 计数是否按实体而非按批次；④ 多入口共用同一常量时终止条件是否字面统一。任何一个不对，批量场景都会放大成小时级浪费或误判。

## v5.1.0 语言归一化 (language-normalize) 经验教训

### 核心改造: BCP-47 -> ISO 639-1

**改造动机**: 旧版 fetcher 写入飞书的是 BCP-47 全称 (`en-US`, `de-DE`), 导致 ScriptPrescreen 豁免判断时 `en-US` 和 `en-GB` 被当成不同语言, 阈值 (`lang_total <= 8`) 失效。

**改造结果**:
- ✅ 新增 `core/language_utils.normalize_language()`, 覆盖 ~80 个 BCP-47 变体
- ✅ fetcher 写入前归一化, ScriptPrescreen 读取时也归一化 (兼容旧数据)
- ✅ 主流语言在飞书中只有一个标识符 (en, de, zh, ja, ...)

**关键设计决策**:

1. **读取时也归一化, 不只是写入时**:
   - 旧 BCP-47 数据 (`en-US`, `de-DE`) 不会自动改写成 `en`/`de`
   - 但 ScriptPrescreen 读取时自动归一化, 保证豁免判断一致
   - 历史数据迁移可以晚点做, 不阻塞新逻辑

2. **大小写不敏感**: YouTube API 偶尔返回大写 (`EN-US`), 归一化函数先 `lower()`

3. **空值/None 透传为 "N/A"**:
   - 不抛异常, 不返回 "unknown" 干扰豁免判断
   - 与现有 fetcher 默认值 `snippet.get('defaultAudioLanguage', 'N/A')` 一致

**踩坑记录**:
- ❌ 第一次实现时 fallback 规则 `len >= 2 and isalpha` 太激进, 把 `xyz` 错归为 `xy`
- ✅ 修复: 4 个明确规则 (BCP47_MAP / 2 字符 / 主标签 / 兜底 N/A), 不再任意截取

**飞书 select 选项迁移提示**:
- 飞书 select(3) 字段接受 option NAME, 不传 ID (参考 feishu-write-safety skill)
- 切换后飞书会自动创建新选项 (`en`/`de`), 但旧选项 (`en-US`/`de-DE`) 还在
- 建议: 先添加新选项 → 跑迁移脚本 → 删旧选项

## 模块化拆分经验 (v3.4.0)

### 拆分时机判断
当一个脚本超过 **500行** 且承担 **3个以上职责** 时，应考虑拆分。

### 拆分原则
1. **单一职责**：每个模块只做一件事
2. **依赖注入**：通过参数传入依赖，而非硬编码
3. **消除全局变量**：将状态封装到类中

### 拆分步骤
```
1. 识别职责边界（如：B站抓取、YouTube抓取、AI调用、报告生成）
2. 创建目录结构（如：platforms/、services/）
3. 逐个迁移函数（保持功能不变）
4. 更新导入语句（相对导入 vs 绝对导入）
5. 验证语法和导入（python -m py_compile）
```

### 导入问题排查
❌ 错误: `from .ai_client import ...` 在直接运行时报错
```python
# 相对导入只在包内有效
from .ai_client import call_api  # 报错: attempted relative import with no known parent package
```

✅ 正确: 使用绝对导入 + sys.path
```python
import sys
import os
sys.path.insert(0, os.path.dirname(os.path.dirname(os.path.abspath(__file__))))
from ai_client import call_api  # 正确
```

### 线程安全封装
❌ 错误: 全局变量散落各处
```python
_last_bili_request_time = 0
_bili_lock = threading.Lock()
# ... 100行后 ...
_last_youtube_api_call = 0
_yt_lock = threading.Lock()
```

✅ 正确: 封装到模块/类中
```python
# bilibili_client.py
_last_bili_request_time = 0
_bili_lock = threading.Lock()

def _rate_limited_bili_request():
    global _last_bili_request_time
    with _bili_lock:
        # ... 限速逻辑
```

### 拆分后的好处
1. **容错隔离**：B站爬虫挂了，只需修 `bilibili_client.py`
2. **降低认知负荷**：每个文件专注单一职责
3. **便于测试**：可单独测试每个模块

## AI审核结果字段规范化 (v3.7.0)

### 问题现象
B站表格的"AI审核结果"字段出现英文值 `safe/unsafe/pending`，且存在不应该存在的 `pending` 状态。

### 根因分析
`video_subtitle_censor7.py:1486-1491` 中B站审核结果写入逻辑错误：
```python

```

### 影响范围
- **B站视频**：3个当天视频显示 `pending` 而非 "通过"/"不通过"
- **统计逻辑**：`workflow_orchestrator.py:784` 用 `"safe"` 检查B站数据导致误判

#### 1. 审核结果值规范
| 平台 | 字段名 | 通过值 | 不通过值 | 禁止值 |
|------|--------|--------|---------|--------|

#### 3. 统计逻辑兼容性

```python
# B站兼容中英文历史数据
passed_values = ["通过", "safe"] if platform == "bilibili" else ["safe"]
```

## 优先级加权"幽灵分"Bug (v3.8.0 修复)

### 问题现象
Bilibili 上有两个视频标注了"高优先级"，但飞书`综合评分`列显示的分数与普通视频无异，没有体现+10分的优先级加成。

### 根因分析
系统采用两阶段分离设计：
1. **评分阶段** (`calculate_full_score`)：接收 `human_priority` 参数但**完全忽略**它，`final_score = content_score * m1_multiplier`
2. **排序阶段** (`filter_and_rank_videos`)：临时计算 `final_score + priority_weight` 用于排序，但**不回写**
3. **写入飞书阶段** (`build_updates`)：读取的是 `score_details['total'] = final_score`（原始值，无优先级）

**本质**：优先级加成分像幽灵一样——排序时出现一次，写入飞书时消失。

### 修复方案 (v3.8.0)
在 `score_details` 构建时直接将优先级加成累加到 `total` 键：
```python
PRIORITY_WEIGHT = {"高优先级": 10.0, "中优先级": 5.0, "低优先级": 2.0, "normal": 0.0}
priority_bonus = PRIORITY_WEIGHT.get(score_result.human_priority, 0.0)
score_details['total'] = round(score_result.final_score + priority_bonus, 2)
```

所有下游的 `build_updates()` ×4处自动继承，无需逐一修改。

### 设计教训
> 📝 **"排序用临时值 vs 持久化值"必须明确区分！** 如果某个计算值需要被外部消费（写DB/写飞书/生成报告），必须在数据产生时就持久化，而不是仅在中间环节临时使用后丢弃。建议：任何影响最终输出的加权因子，应在 `score_details` 构建阶段就完整包含。

### 双分制设计决策
修复过程中确立了新的评分展示策略：
- **综合评分/Total Score** = 排序评分（含D1+D2+D3+D4+M1+优先级）→ 决定排名
- **D4吸引力分/D4 Appeal** = 内容评分（纯AI判断内容质量）→ 衡量价值

这样人工看飞书时能一眼区分"排第一是因为真的好"还是"因为被标了高优先级"。

## YouTube评分"半残"Bug (v3.9.0 修复)

### 问题现象
YouTube视频的综合评分长期只有B站的一半左右（约5分 vs 10分），用户误以为是设计意图（5分制 vs 10分制），实际是数据丢失导致的伪象。

### 根因分析
数据在**两个环节**丢失：

1. **字幕阶段断裂**：`_youtube_base_result()` 硬编码 `views=0, likes=0, comments=0, publish_time=0, channel_id=''`，丢弃了抓取阶段已获取的全部统计数据

2. **评分公式人为禁用**：`calculate_full_score()` 的YouTube分支显式 `D2=0("YouTube无时效数据"), D3=0("YouTube无互动数据")`，即使数据传入也被丢弃

3. **结果**：YouTube退化为 `(D1 + D4) / 2` 两维评分，且D4经常为0（AI未审查时），实际只剩 `D1/2`

### 数据可用性确认
YouTube Data API 在抓取阶段（`bilibili_youtube_once_for_all_fetcher.py`）已完整获取以下字段并写入飞书：
- `Views`, `Likes`, `Comments` → 可直接用于D3互动分计算
- `Published At` → 可解析为时间戳用于D2时效分计算
- `Channel ID` → 可用于M1新人修正系数

### 修复方案
采用**双管齐下**策略：

1. **数据回填**：在 `calculate_video_score()` 中，YouTube视频评分前自动从飞书读取该视频的统计记录，回填 views/likes/comments/publish_time/channel_id

2. **公式升级**：YouTube分支改为动态维度平均：
   ```
   valid_dims = [D1, D4]
   if D2 > 0: valid_dims.append(D2)
   if D3 > 0: valid_dims.append(D3)
   content_score = sum(valid_dims) / len(valid_dims)
   ```
   - 完整数据时：`(D1+D2+D3+D4)/4` — 与B站完全一致
   - 缺失D2/D3时：`(D1+D4)/2` — 向后兼容旧数据（无飞书记录的视频）

### 设计教训
> **跨模块数据管道必须有端到端的验证！** 抓取→存储→初筛→字幕→评分是一条长链路，每一步都可能丢失字段。当发现某个平台评分异常偏低时，应首先追踪完整数据链路而非假设是"设计如此"。建议：在每个模块边界添加关键字段的断言或日志，确保核心数据不静默丢失。

## IP被阻止误报 + 智能重试引擎 (v4.4.0 修复)

### 1. 子串匹配是异常分类的天坑

**问题现象**：脚本运行时大量出现"IP被阻止"提示，但实际是视频本身无字幕或区域限制。

**根因**：`platforms/youtube_client.py:163, 179` 使用了子串匹配：
```python
if 'IpBlocked' in err_str or 'blocked' in err_str.lower():
    is_ip_blocked = True
```

`err_str.lower()` 包含 `'blocked'` 这个子串，意味着任何带 "blocked" 的字符串都会被判定为 IP 阻止，包括：
- `RequestBlocked`（视频级限制/区域限制） — 最常见
- `subtitles are blocked`（无字幕的措辞）
- 任何错误消息里出现的 "blocked" 单词

**最严重场景**：循环遍历 10+ 种语言字幕时，**任意一种**抛 `RequestBlocked` 都会把整个视频标记为 IP 阻止，触发级联退避。

**修复方案（v4.4.0）**：
1. **三级分类**：异常类型名 → 字符串精确匹配 → 短语整词匹配
2. **绝不单独匹配子串 "blocked"**：宁可 unknown 也不误判
3. **单条 transcript 失败不传染**：每个 `transcript.fetch()` 单独 try-except，只有该语言抛 `IpBlocked` 才跳出
4. **错误分类粒度从布尔变 8 维**：ip_blocked / rate_limit / no_subtitle / region_locked / video_unavailable / transient_network / feishu_throttle / unknown

**关键代码**：
- `core/smart_retry.py:classify_youtube_transcript_error()` — 三级分类器
- `platforms/youtube_client.py:_classify_youtube_error()` — 适配层
- 12 个测试用例全部通过，包括关键的"RequestBlocked - sub videos for this language are blocked" 旧 bug 场景

**经验总结**：
> ⚠️ **错误分类的第一原则：宁可 unknown，绝不误判**。一个误判会触发级联退避（IP 阻止 → 等待 5 分钟 → 整批暂停），影响远比"标为 unknown 但稍后重试"更严重。子串匹配在错误信息处理中是反模式，必须用异常类型优先、字符串精确匹配、整词匹配三级回退。

### 2. "立刻重试"是无脑设计

**问题现象**：当前重试逻辑：失败 → 立即重试 → 同样失败 → 立即重试 → 永远失败。

**根因（旧 retry_failed_youtube_v2.py）**：
- transcript_api 失败 → 调 yt-dlp
- yt-dlp 失败 → `tracker.wait()` 等待 5~300 秒
- **等待完了还是用同一个 IP**继续打，100% 还是被封
- 时间上限仅 5 分钟，而 YouTube IP 封禁窗口通常 10-30 分钟
- 不区分错误类型，所有错误都重试

**修复方案（v4.4.0 SmartRetryEngine）**：
1. **错误分类前置**：8 种错误类型，每种不同策略
2. **被动 → 主动**：连续 IP 阻止 ≥ 3 次时**主动暂停**并提示用户换代理
3. **IP 健康度滑动窗口**：5 分钟内成功率 < 30% 触发"整批暂停"
4. **视频级问题智能跳过**：no_subtitle / region_locked / video_unavailable **不重试**（重试也解决不了）
5. **时间预算**：单次运行最多 30 分钟，超出强制停止（避免一次运行耗 2 小时）
6. **两阶段流程**：阶段 1 先跳过失败 → 写报告 → 写飞书 → 阶段 2 仅重试失败 → 追加报告 → 写飞书

**策略表**（核心）：
| 错误类型 | 重试次数 | 等待序列 | 额外动作 |
|---------|---------|---------|---------|
| IP 阻止 | 3 | [60, 120, 300] | 提示换代理 |
| 频率限制 | 2 | [30, 60] | 降低并发 |
| 网络抖动 | 3 | [2, 5, 10] | 同 IP 重试 |
| 无字幕 | 0 | [] | 直接跳过 |
| 区域限制 | 0 | [] | 直接跳过 |
| 飞书限流 | 3 | [5, 15, 45] | 退避+降级 |

**关键代码**：
- `core/smart_retry.py:SmartRetryEngine` — 决策器
- `core/smart_retry.py:TwoPhaseRetryCoordinator` — 两阶段协调器
- `tools/retry_failed_youtube_two_phase.py` — 新建的两阶段重试脚本

**经验总结**：
> 🧠 **重试的三个反模式**：
> 1. 用同一 IP 死磕（无效重试）
> 2. 把所有错误等同处理（无差别重试）
> 3. 永远不放弃（无时间预算）
>
> 正确做法：按错误类型分级 → 按健康度暂停 → 按预算放弃 → 两阶段让用户看到中间结果。

### 3. 飞书同步应分阶段，避免"长重试"期间状态不一致

**问题**：原重试脚本只在最后一次性同步飞书，长达 2 小时的运行期间用户看不到进度。

**修复**：两阶段流程中，**每个阶段结束后**立即同步飞书：
- 阶段 1 结束：标记成功的为 success，标记失败的为 pending 或 failed
- 阶段 2 结束：更新重试结果，标记仍失败的

**好处**：
- 用户可随时看到中间进度
- 阶段 1 失败不阻塞 AI 审核后续环节（pending 状态可被其他流程处理）
- 重试成功立即可见（不用等全部跑完）

**经验总结**：
> 📊 **长任务必须有阶段化反馈**。一次性同步会让用户在最后 10 分钟里无法判断"系统卡了还是快完了"。阶段化同步是降低用户焦虑感的最直接手段。

## 比率类指标小样本门槛规避 (2026-08-19 修复)

### 问题现象
互动率 = (点赞+评论)/观看。当观看数极小时（如 3 次观看 + 1 个点赞），互动率虚高到 30%~100%，三张表（目标表 / 频道表 / 视频表）均受影响。同类小样本问题波及所有「分子事件计数 / 分母小样本」型比率指标。

### 规避方案（最小样本门槛：不达标 → 该字段置空）
| 表 | 字段 | 门槛 |
|----|------|------|
| 视频表 | 点赞率/评论率/互动率/观赞比 | 观看数 ≥ 100 |
| 频道表 | 游戏相关互动率 | 该游戏总观看 ≥ 200 |
| 频道表 | 游戏相关投入度 | 频道总视频数 ≥ 5（同时重算贡献分，focus 置默认 1.0） |
| 频道表 | 游戏相关爆款度 | 该游戏中位观看 ≥ 50 |
| 频道表 | 游戏相关直播占比 | 该游戏视频数 ≥ 5 |
| 频道表 | 月更新频率/平均间隔 | 该游戏视频数 ≥ 5 |
| 目标表 | 互动率/贡献分/投入度/爆款度 | 从频道表同步（口径一致） |

**不设门槛的比率字段（经核查无小样本虚高问题）**：
- 观看占比（该游戏总观看 / 频道总观看）：有界 0~1，高占比样本集中在垂直频道，语义真实合理，非样本偏差。
- 相对频道均观：极端值样本的频道基数普遍很大（总观看数万级、视频数上百），分母稳健。

### 关键代码位置
- `fill_mining_tables.py`：计算阶段已按门槛只对达标记录写入比率字段（源头预防）
- `fix_rate_thresholds.py`：对已有存量数据按门槛批量清空 + 目标表同步（`--apply` 执行）

### 设计教训
> 📝 **凡「分子为事件计数、分母可能很小的比率」必须先设最小样本门槛，否则 1 个偶发事件（1 点赞/1 评论）就能制造 100% 的假信号。** 门槛选择应兼顾「过滤小样本噪声」与「保留可用数据量」，并同步多表口径一致。反例验证：有界比率（观看占比）和分母为大数集合的比率（相对频道均观）不受此问题影响，不必误伤。验证方法：修复后对每个比率字段统计「观看<门槛且比率>50%」应降为 0。

## 跨表批量写入的通用踩坑（2026-08-21 / 08-22）

> 以下为跨表批量写入时反复踩到的坑与可复用结论。

### 飞书 API 行为
- `batch_create` / `batch_update` / `batch_delete` **一律 POST**；用 PUT 会报 `99992402 field validation failed`。
- 更新字段必须 `PUT /fields/{field_id}` 且 body **必含 `type`**，即使只改名也要带。
- 数字字段读回可能是 **字符串**：跨表复制时按目标字段类型转换，`type=2` 一律 `float(str(v).replace(",", ""))`，否则报 `1254061 NumberFieldConvFail`。
- 多选字段必须传 **option 名列表**，不能传逗号字符串，否则 `1254063 MultiSelectFieldConvFail`。
- `type=15` 的 URL 字段读回是 `{"link": ..., "text": ...}` dict；`type=5` datetime 为空时应**跳过字段**而非写空串。
- 报 `1254045 FieldNameNotFound` 时，先用 `repr()` 打印字段名核实（是否带前导空格 / 是否已改名），并用单条创建做冒烟测试后再全量写。

### 数据一致性
- **跨表复用前必须重新拉取目标表字段类型**：同一逻辑字段在不同表可能建为文本 / 多选 / 数字，旧脚本按字符串写入会整批失败且异常被吞掉。
- 分钟 → 小时换算用 `round(x, 1)` 而非 `int()`，否则不足 1 小时的记录被截成 0。
- 多年度数据表，时长字段必须明确「累计」还是「单年」；两者并存时允许 ≤0.2 的舍入差。
- 目标表已非空时，写前先确认是否有**旧版字段残留**，按旧字段名精确清理，不能只依赖通用占位判定。
- 飞书建字段后会自动生成带默认值的**占位行**，会让计数虚高；按业务主键为空识别并删除。
- 排序前先转数值：`float(x.get(...) or 0)`，否则 number 字段读回 `str` 时报 `bad operand type for unary -`。

## v5.3.8 Discord 自荐标记修正 + ScriptDedup 全局去重 经验教训

### 根因与修复

1. **"强行入选"(Selected) 与"优先级"(Priority) 是评分体系两个不同维度，不可混用**: `Selected` 在 `PRIORITY_WEIGHT` 里是 `normal`/`""` → +0 加权（"强制入选、不加分"），而"自荐优先"需要的是 `High Priority` (+10 加权)。Discord 自荐标记写 `Selected` 导致本周 12 条自荐视频全部体现为 0 优先级、淹没在 44 条脚本优选里。教训：**给业务语义（自荐=优先）选字段值时，必须查清该值在评分/排序链路里的真实含义，不能凭字面"Selected≈选中"想当然。**

2. **去重必须跨分组维度 + 排除已标记记录**: 旧 ScriptDedup 先按语言分组、组内再按 UP 去重，同 UP 在 en/ru 两语言组各留 1 条 → 跨组重复；且已标记 UP（Discord 自荐/中文精选）的其他视频仍进入候选池被选中。教训：**去重键（UP）必须在全局集合上做，且"已有代表视频"的状态（已标记）要作为排除条件参与去重，不能只看待处理候选本身。**

3. **数据修复脚本要"重取字段类型 + 三重定位 + 试点回读"**: 修飞书历史数据前 `get_fields` 重新拉表结构校验 select(3)/number(2) 类型；目标记录用"来源标注 + 当前值 + 今日创建"三重条件 + 与已知 ID 交叉核对定位，避免误改；`--pilot` 先修 1 条并回读验证，通过后才 `--full`。这与 workspace 规则"写飞书前重新获取字段类型"一致。

### 可复用结论

- 优先级加权值：High=+10 / Medium=+5 / Low=+2 / Selected(强行入选)=+0（`feishu_fields.PRIORITY_WEIGHT`）
- Rating 等级由 Total Score 判定：>=10 为 A（`scoring.get_score_grade`），故优先级视频 +10 后几乎必为 A 档
- 正向标记全集 = {Selected, High Priority, Medium Priority, Low Priority}，retry 过滤器与 ScriptDedup 排除逻辑应使用同一全集（SSOT），避免两处口径漂移

## v5.3.9 ScriptDedup 恢复按语言分组去重 经验教训

### 根因
v5.3.8 把 ScriptDedup 去重从"按语言分组"改成"全局按频道"，误以为"全局去重更严格就是更好"。但去重分组维度是**业务语义**：本项目按语言面向不同受众，同一 UP 的英文视频和俄文视频是给不同观众看的，应各自保留 1 条代表。全局去重会错误地把跨语言视频也砍掉。

### 教训
1. **去重/分组维度属于业务规则，不是纯技术优化**：修改前必须向用户确认"按语言还是全局"，不能凭"更严格=更正确"想当然。本次先改了全局，用户一句"某一个语言下"才纠正回来。
2. **"已标记 UP 排除"的作用域要跟随去重维度**：按语言分组去重时，"该 UP 已有代表视频"的排除也必须在语言组内做（en 组已标记不影响 ru 组），否则会误伤跨语言候选。
3. **补足阈值判断要对齐"有效入选"口径**：语言组内 `有效入选 = 该语言已标记数 + 脚本保留数`，< 8 才补足；补足池只取"同频道多余"（`_decide` 丢弃的），不取"已标记 UP 排除"的（那些 UP 已有代表，不应再补）。

### 可复用结论
- 按语言分组去重：`by_lang[lang]` → 组内 `by_author` → 每频道 `_decide` 留最新 1 条 → 有效<8 时从 fill_pool 补足
- 跨语言去重保留（同 UP en/ru 各 1 条），仅语言组内去重 + 组内排除已标记 UP
